### 1.1 C1 (b) design note — lid-aware timer tiebreak (ready, **not** applied: decision (a))
**Today** (`Shared/FinalRules.cs:67-76`): timer survivors sort by `Deepest` (deepest *crumble* shelf, `grid.Shelf(tile)` of `Hazards.Grids[0]`), then `Tiles` (distinct crumble tiles touched), then slot. `OnRushTick` (`:29-63`) only updates them when a crumble grid and a `ReactiveSet` exist (`rx == null → continue`, `:45`). Lid Flip has `LidGrids` and no `Grids`, so both are 0 for everyone and **slot decides**.

**(b), if chosen — shared `FinalRules` only, deterministic, `ruleset_v1.json` / `map_pool_v1.json` / `movement_v2.json` untouched:**
1. Lid mode = `Hazards.Grids.Length == 0 && Hazards.LidGrids.Length > 0` (fixed per round; the crumble path stays exactly as it is, so the sandbox / crumble tests and their hashes do not move).
2. Two new `TimedRoundRules.Player` fields (ints, reset in `Begin` like the others): `LidShelf` = index in `LidGrids` of the grid the player last stood on (0 = top `cs_lids_top`, 1 = lower `cs_lids_low`), `LidFalls` = how many times `LidShelf` increased. Updated in `OnRushTick` for in-play, active, grounded players only: `g` = the first grid whose `LidUnder(PosX, PosY, PosZ) ≥ 0` (feet within ±10 cm of its top, `LidGridDef.cs:82-93`); if `g > LidShelf` then `LidFalls++`; `LidShelf = g`. Pure integer state from the simulated `MotorState` (the same on server and in every replay: no floats, no RNG, no wall clock).
3. `Tiebreak` in lid mode: `LidShelf` ascending (top beats lower), then `LidFalls` ascending, then slot. `Rank`'s `values` in lid mode = `LidShelf * 1000 + LidFalls` (display / QA only: the transcript hashes placements and reasons, `MatchDirector.cs:710` / `:721`, not values). `ByteValue` / `StateEntries` (the race byte and rstate) unchanged, so no protocol or HUD byte changes.
4. Outs keep their order (last out first, `:93`); the tiebreak only orders players who left in the same tick.
5. Note for the user: under movement v2 nobody gets back from the lower shelf (6 m below; hop 1.2 m, no springs), so for timer survivors `LidFalls` is 0 on the top shelf and 1 on the lower one: "fewer falls" adds nothing today and **two survivors on the same shelf are still ordered by slot**. A finer key that would separate them (e.g. "dropped to the lower shelf later ranks higher", or "fewer lids stood on") is a further rules choice; the note above implements exactly the brief's (b).
6. Tests (new `FinalTiebreakTests` cases in EditMode): (i) same inputs → same order (two `Round<FinalRules>` runs with an identical scripted world → identical `RoundOutcome.Order`); (ii) both shelves: survivors on top rank above survivors on the lower shelf regardless of slot; (iii) a tie down to slot (two top-shelf survivors with 0 falls → lower slot first); (iv) the crumble path unchanged (the existing `M4RulesTests` "higher layer, then fewer tiles, then slot" case still passes). Then re-run Final QA (`g1-qa.sh` / `m4-qa.sh` on `CrumbleShelf`): only the order of timer endings can change (0–3 % of normal rounds), not durations, falls or fairness.
7. Doc 08 §7 + doc 15 G4.5-8 → (b), Notes for M6: "Final timer tiebreak on lid maps = top shelf > lower > fewer falls > slot" (a ruleset v2 rules note).

### 1.2 C2 — Star Fountain: 1 whole-run hazard mismatch at round end → Champion
**Finding: a counting artefact, not a hazard desync.** Hypothesis with evidence (the log is still in `.m1-logs/`):
- **Where it was counted:** `.m1-logs/probe-g44-local-r2-2.log:121`, the 10 s window at server tick ≈ 3 092: `phase=Ended`, `match=Champion`, **`corrections=0 pushCorrections=1 hazMismatch=1 hazardCorr=0 respawns=0`**, `predHits` 1 → 2 (the client predicted a sweeper hit in that window).
- **Why it is a push, by elimination** (`Net/ClientPrediction.cs`): `HazardMismatches++` happens at `:249-252` whenever the stun / immunity state differs at S, **before** the snapshot's cause is classified. A stun difference also sets `flagsDiffer`, so that reconcile must have been counted in exactly one of: `Corrections` (`:270-280`, would show `corrections ≥ 1` → it is 0), `Respawns` (`:258-263` → 0), or `PushCorrections` (`:265-269`, the server reported a player–player push since the last snapshot, `SnapHeader.EventPushed`) → **1**. So the one mismatch is a snapshot where the server's soft separation (server-only by design, R14, not predicted) moved the player, and the server's sweeper contact then differed from the predicted one (hit vs no hit). `HazardCorrections` (`:273-274`) is only counted in the non-push branch, which is why the in-round `hazardCorr` stays 0.
- **Why at round end:** after `RoundEnded` the round keeps simulating in-play players (`TimedRoundRules.cs:179` `Simulates` = `InPlay`) with neutral input (`:178`, and the client's `ClientSim.InputLocked` for `Ended`), the sweepers keep turning, and the 12 players stand packed where the timer caught them — pushes next to a moving sweeper bar are most likely then.
- **Not a tick / seed reset:** hazard time is `tick − RoundStartTick` on both sides (`HazardSet.cs:159`); `RoundStartTick` and the seed change only with a new `RoundParams` (`ServerMatch.LoadMap`, `:208`), which the client adopts by rebuilding its prediction (`ClientSim.EnsurePrediction` / `SameRound`, `:567-593`). That happens at the lobby load after `Done`, not in the Champion window: the round message in this log comes after the `match=Done` windows.
- **Planned fix (phase 2, dev statistics only, no gameplay / protocol change):** count a hazard mismatch only when the difference is unexplained — after the respawn / teleport and push checks — and keep the push-explained ones in a separate `PushHazardMismatches` counter (logged next to `hazMismatch` in `GateLogger.cs:135`, summed in `m2-summarize.py`). EditMode test: a reconcile with `EventPushed` and a stun difference leaves `HazardMismatches` at 0 and counts `PushHazardMismatches`; an unexplained stun difference still counts. Then re-run `scripts/g44-probe-local3.sh` once. If phase 2 instead finds a mismatch with `pushCorrections = 0` and `respawns = 0` in its window, that would be a real desync and gets debugged instead (`LastMismatchAuth / Predicted` logged at that tick).

### 1.3 C3 — Lid Flip at 150 ms: rare large corrections (max 57 / 115 cm)
**Finding: no tick mismatch in the lid path.** Read:
- Lid colliders (both grids) are switched in `PhysxMotorWorld.BeginTick(tick)` from `HazardSet.LidStatesAt(tick)` (`Net/PhysxMotorWorld.cs:92`, `:122-133`): one array, grid by grid (top then lower; `HazardSet.cs:121-140`), the same order as the colliders (`LidFlipTests.TwoGrids_ColliderAndViewOrder_MatchLidStatesAt`, `LidFlipTests.cs:263`).
- The server calls it with the tick it simulates (`SimCore.Step`: `Tick++`, `_world.BeginTick(Tick)`, then `PlayerStep.Run(…, Tick, …)`); the client calls it with the **predicted tick of each step**, in fresh prediction and in every replay (`ClientPrediction.StepOne`, `:392-395`, from `Predict` `:167-176` and `Rewind` `:348-366`). Hazard time = `tick − RoundStartTick` on both. So a lid opens under a predicted player at the same tick as on the server, and the lower shelf's colliders are at that tick too. The probe agrees: **0 hazard mismatches** and 0 hazard corrections on every leg (G4.5 §5), and localhost has 0.00 corrections.
- The view is posed at the predicted timeline too (`ClientSim.HazardRenderTick`), so what you see is what you stand on.

**Hypothesis for the large ones:** a small server-only difference at a lid edge becomes a fall-vs-stand difference, and a fall diverges fast (≈ 0.8 m vertical over the ≈ 0.4 s of lead + replay at 150 ms RTT). The small difference comes from what the client cannot predict:
1. **Server-filled input**: at 150 ms + 2 % loss a lost TCP segment stalls the input stream for ≈ RTT + RTO (≥ 400 ms, more than the 6–7-tick lead); the server then simulates those ticks with the previous command for 3 ticks and neutral after (`InputSanitizer.RepeatTicks = 3`, `InputSanitizer.cs:54`, `:187-200`), while the client predicted its real commands. The server log counts these (`late= repeated= neutral=` per 10 s).
2. **Pushes**: the 12-player probe packs the inner 3 × 3; the two big corrections sit in the windows with the most push corrections (`.m1-logs/probe-g45-150-3.log`: 115 cm in a window with 11 push corrections, the player airborne at y 7.0; `probe-g45-150-2.log`: 57 cm with 3). A push is flagged only on the snapshot that covers it; its effect near an opening can still differ later.
- It is **not Lid-Flip specific**: the same probe at 150 ms shows max corrections of 110 cm on Star Fountain (`g44-150-3`) and 58–60 cm on Capsule Run (`g42-150`). The rate stays under target on Lid Flip (0.00 / 0.09 / 0.18 non-push per 5 s).
- **Planned (phase 2):** the `g47-qa-all.sh` 150 ms leg keeps the dev server's log for that leg (`.m1-logs/g47/server-g47-CrumbleShelf-150.log`) next to the probe client logs; line up each large correction's 10 s window with the server's `late / repeated / neutral` and push counters. If they line up → **document as expected under 150 ms + loss** (the fix would be in the transport / lead, not cheap, not a gameplay change). If a large correction has no late input and no push in its window → look for a real tick mismatch (log `LastMismatchTick / Auth / Predicted`). Target unchanged: ≤ 0.4 non-push / 5 s, 0 hazard mismatches.
