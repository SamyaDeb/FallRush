## 2. Rounding and determinism rules

- **One rounding helper:** `fx::div_round` (half away from zero) for every division, `fx::round_shift` for shifts
  (= `HazardMath.RoundShift`). Documented floor divisions: hazard time sampling (`floor_div`, `t30 = ⌊t60/2⌋`) and the
  C# ports that floor on purpose (door ramps, goo rise, `TileUnder`, `LidUnder`, lid wave counts), each marked
  `// floor (C#: …)`.
- `i64` intermediates everywhere; `i128` only in `mul_div`, ray slab compares and `isqrt_u128` (capsule ray).
- Fixed order: slots ascending, colliders ascending (bitset candidates), separation pairs (i < j) in slot order.
- No `HashMap`, no recursion, no allocation in `step()` (the crate has no `alloc` outside the off-chain `builder`
  feature); every loop has a compile-time maximum (`MAX_SUBSTEPS` 64, `TOI_BISECT` 8, `MAX_CANDIDATES` 64,
  `MAX_QUERY_CELLS` 64, slide iterations ≤ 8, lid waves ≤ 64, …).
- Floats: none in `src/` (`#![deny(clippy::float_arithmetic)]` + `tests/float_oracles.rs::no_floats_in_src` scans
  every source file); floats only in `tools/gen-trig`, the test oracles and `rush-sim` reporting.
- Tick rate is a parameter (15 / 20 / 30 Hz): every ms constant → ticks with round half up; hazard time is kept in
  1/60 s (`t60`), exact at every supported rate; hazard defs keep their authored 30 Hz tick values (ms timing unchanged).
- sBPF stack frames are 4 KB: candidates are index-only, lid scratch is `u8`, `World::reset` initialises in place.

## 7. Intentional differences from Classic

1. Velocity is in mm/s (C# uses cm/s) and positions in mm. The rounding is documented in §2.
2. Collision is our own integer kit, not PhysX: an upright capsule against OBB, prism, sphere and capsule shapes. Sweeps sample
   every ≤ 200 mm, then do 8 bisection steps for the time of impact. As in PhysX `CapsuleCast`, a collider the capsule already
   overlaps at the start of a sweep is ignored. Rounded capsule edges ride over a lip up to the sphere centre, the same as PhysX.
3. Windows authored in ms become whole ticks per rate (§5).
4. At 15 Hz, two reference traces drift past the pass bar with the **same outcome**: dive-slide-cancel (final drift 325 mm) and
   rolling-ball (566 mm, the hit lands one tick apart). They are **open** until the user accepts them as a 15 Hz difference (§9).
5. Bots: the C# BotBrain is ported with the full 7-heading ball dodge and a first-order steering lag for reaction time
   (Easy 8 / Normal 5 / Good 2 ticks). Bot randomness uses rush-core's seeded Rng, not `System.Random`, so individual runs differ
   from Classic and only the distributions are compared (§10).

## 12. Compute-unit outlook

Real maps, 12 bots, 60 s, `rush-sim counters` (`docs/proof/p1/qa/counters.md`). Per tick at 20 Hz:

| map | narrowphase p50 / p95 / max | sweeps p50 / p95 / max | bisections p50 / p95 / max |
|---|---|---|---|
| Capsule Run | 199 / 294 / 345 | 28 / 34 / 39 | 112 / 168 / 198 |
| Goo Tower | 218 / 383 / 590 | 26 / 46 / 71 | 104 / 168 / 272 |
| Star Fountain | 169 / 278 / 351 | 30 / 42 / 46 | 64 / 104 / 136 |
| Lid Flip | 108 / 144 / 182 | 12 / 14 / 17 | 72 / 96 / 104 |

15 Hz and 30 Hz are within about ±10 % per tick (`counters.md`).

- **Measured CU (sBPF, LiteSVM):** LiteSVM, `world_v1`: 40 ticks × 12 random-input players on the vector map cost **19.7M CU per case
  ≈ 493k CU per tick** (max chunk 83M for 4 cases). `motor_v1`: 213k CU per 8-tick single-player case ≈ **27k CU per
  player-tick**, so ≈ 320k for 12 players before hazards, separation and bots. This is **above the 400k CU a timed-task
  execution gets** (P0 §3.1) and above P0's own spike (p50 142k). rush-core is the full C# motor (sweeps + 8-step TOI
  bisection + slide iterations + closest-feature narrowphase), not P0's simplified probe. **P0-1 stays open.** P1b needs
  a CU pass: fewer bisections (8 → 4), cheaper touch tests before closest-feature, per-player AABB reject for moving
  hazards, and splitting players across instructions or ticks. Native counters per tick are above; CU on the real maps
  inside the rollup is UNVERIFIED.
- **P0 conversion (order of magnitude):** P0 measured 221–329 CU per OBB test and 557–675 per prism
  (`P0-feasibility.md` §3.1, devnet-as). rush-core's narrowphase is closest-feature distance, not P0's touch test, so
  it costs more per test. P0's own conclusion holds: a timed-task execution has **400k CU**, and full 12-player ticks on the
  real maps will need the split and P1b work (cheaper narrowphase, fewer bisections). **UNVERIFIED** until P1b measures
  `step()` on the rollup.
- Native: 0.12–1.8 ms per tick with the counters feature on (M2, shared machine).
- The full sBPF report is in `docs/proof/p1/sbf-parity.txt` (LiteSVM 0.9.1, `cargo build-sbf`, Solana 3.0 crates).
