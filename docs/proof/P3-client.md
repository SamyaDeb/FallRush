# P3 — the Unity on-chain client (proof)

Branch `p3` in `../FallRush-p3` (off `main` @ `2decc78`, `main` @ `c534e37` merged in after P2). Prompt:
`docs/prompts/P3-PROMPT.md`. A number is measured only where it says so; everything else is **UNVERIFIED**.

**Summary.** Lid Flip Finals run on the MagicBlock rollup with you in them: Mac player (and WebGL, §8). 15 devnet
Finals and 1 hybrid match completed; in all of them the champion on screen matched the on-chain `Match`. In the
user's feel test (3 devnet Finals) on-chain felt **as good as Classic, nothing laggy**. The automated correction
target (< 1 per 5 s) is met on the emulator (0.08) and the local stack (0), but on devnet only in 2 of 5 runs
(2.4–7.6 in the others). The rest of the corrections come from input transactions that sometimes take 0.5–1 s to
land.

## 2. The chain bundle (B) — `packages/chain` → `StreamingAssets/fallrush-chain.js`
- One esbuild IIFE, 371,999 B (112,166 B gzip), loaded lazily by on-chain play only. Config-driven:
  `config/emulator.json`, `local.json`, `devnet.json` (P2 §10 + the `Arena` layout checked on devnet: 1,432 B;
  P2's proof says 1,904 by mistake).
- Wallet: a burner in localStorage (exportable, never logged); our own TS `SessionTokenV2` (session-keys 3.1.1:
  `create_session_v2` `dfe96c0741c2eb26`, PDA `["session_token_v2", target, signer, authority]`, revoke
  `d33b7dbc2b9b0866`); Phantom connect only.
- Rollup transport: `join_lobby` with the session signer + token (or the burner), `submit_input(slot, start,
  [u8;12])` (cam yaw >> 8), base layer throttled ≤ 1.5 tx/s, confirms by `getSignatureStatuses`, Cloner retry.
  **World subscription = plain `accountSubscribe` on 2 redundant sockets, each reopened after 600 ms of silence**
  (measured: web3.js `onAccountChange` in this bundle went silent for seconds on devnet-as while a raw socket got
  all ~90 notifications/s), plus a 1 s backup poll; only `part_pending = 0` snapshots (complete ticks) are passed
  on; a new match = the tick restarts below 30.
- `tools/p3/chain-relay.mjs`: the bundle in Node behind the emulator protocol (ws://127.0.0.1:8788) so the Mac
  player can use the real rollup; keys in `tools/p3/.relay-keys` (600, gitignored); every SOL movement printed.
- Tests: 39 bundle (Node runner) + 4 relay + `tools/p3/frc-jslib-test.mjs` (the `FallRushChain.jslib` glue + the
  bundle against a live emulator: boot, join, subscribe, 46 Worlds in 1.5 s, input confirm).

## 3. The emulator (C) — `tools/chain-emulator`
Node, no npm deps, P2's rush-core at 30 Hz; wire format `docs/proof/p3/wire-v0.md`; default port **8797** (8787
clashed with a local wrangler dev server). 20/20 tests: the World hash equals the client core's at every tick over
900 ticks. Shaping is 45 ± 10 ms with 0.1 % loss; there is `/final` for the switch.

## 4. On-chain session + prediction (D)
- Entry: menu "Play On-Chain (preview)" (dev builds), `?onchain=emu|local|devnet`, `-fallrushOnchain …`, or the
  switch. The Classic screens run unchanged through `ClientSim.Feed` (additive; null in Classic). The chip is set via
  `ChainAdapters.Override`.
- Prediction: inputs are stamped T+3 in batches of 3 (one transaction per 100 ms), plus an **adaptive extra lead
  of +0..+3**, raised when the arena's `applied_tick` shows our ticks arriving late and capped by the program's
  +8 window. Every World rebases the prediction: set the World, then replay with full rush-core steps (bots exact).
  Corrections over 5 mm are counted; 120 ms smoothing, 2 m snap. The clock comes from World arrivals (nominal 30/s,
  or the measured rate if the chain is clearly slower), "! LAGGING" after 300 ms, F3 tick health, 60 fps cap.
- Measured, Mac player, emulator (RTT ~110 ms, 0.1 % loss): **0.08 corrections / 5 s** (max 1, 13 windows),
  30 updates/s, 10 batches/s, 0 rejected.
- Measured, Mac player, local stack (P2's mb-stack, 20 ticks/s): a whole Final with 0 corrections and 0 late
  inputs (2,196 exact matches). Confirms often time out on this overloaded machine (these are counted as
  "unconfirmed", not rejected).

## 6. Classic → on-chain switch (F, M) and spectating (G)
- Server (additive, off by default: `-fallrushOnchainFinal`), `ChainFinalHandoff`:
  - **emu:** at the last round, `POST /final` with the alive roster + hazard seed; the round waits ≤ 8 s until the
    arena steps.
  - **devnet / local** (`-fallrushOnchainFinalNet devnet -fallrushOnchainArena … -fallrushOnchainWorld …`): at
    roster lock clients get `fonc final_prejoin` (match id, their Classic slot) and pre-join the arena lobby.
    P2's keeper (`MODE=hybrid`, unmodified) bridges rounds 1–3 from the server's jsonl and calls `start_final`.
    "Live" = Arena RUNNING + WorldAcc round 4 + the tick advancing.
  - Live: `ChainFinalRules` (no server simulation; the result comes from the arena) + `fonc final_onchain`. Not
    live: the server plays the Final itself.
- Client: `OnChainSwitch` → `OnChainSession.StartFinal` (own slot, or spectate). After the server reaches CHAMPION
  the screens are handed back to it; the chip / receipt stay on-chain (Rollup ✓, `Match` + arena explorer links,
  Solana ✓ once the `Match` account is owned by the program on Solana again).
- G: `?onchainspectate=1` / `-fallrushOnchainSpectate`; eliminated players spectate automatically (Tab camera).

## 13. Requests for P2
1. Bump `rush_core::VERSION` (or expose a core hash) when behaviour changes (TOI 8 → 6 kept 0x10001), and put it in
   `WorldAcc`, so a client can refuse a mismatched arena.
2. A restart counter (match serial) in `WorldAcc`: clients now infer a new match from the tick restarting.
3. Fix P2 proof §2: `Arena` is 1,432 B, not 1,904.
4. The keeper opens the lobby and calls `start_final` with no wait for humans (synthetic Finals): a "wait for N
   human joins / T seconds" option would make human Finals deterministic (P3 joins in the rounds-1–3 window and
   predicts the keeper's synthetic finalists).
5. Input latency: occasional 0.5–1 s confirms for `submit_input` on devnet-as are the main source of corrections.
   A wider accept window (> +8) would let the client lead further.
